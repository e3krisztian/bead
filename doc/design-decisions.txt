P: how to create beads of the same kind (for versioning and lineage)
D: bead kind is a UUID that must be copied from existing bead, only `edit` preserves kind
   - Same kind: `edit` existing bead, modify content, `save` (copies the UUID)
   - Different kind: `new` creates fresh workspace with new UUID
   - Name changes: rename workspace directory before `save`, or rename archive after `save`
   - Kind UUID is immutable identifier that links beads in same lineage/family
   - This ensures kind represents actual logical data compatibility


P: input update should ensure precise upgrade coordinates to prevent accidental data lineage breaks
D: strict (name, kind) matching by default with explicit relaxation options
   - Historical progression: kind-only (pre-2019) → name-only (2019-2025) → name+kind (2025+)
   - Default: `input update` matches by both input name AND kind for precise upgrades
   - --no-kind: relaxes to name-only matching (preserves 2019-2025 behavior)
   - --no-name: relaxes to kind-only matching (preserves pre-2019 behavior)
   - Mutually exclusive options prevent conflicting matching modes
   - Explicit bead references (paths/names) bypass all matching constraints
   - Helpful error messages suggest relaxation options when strict matching fails
   - No automatic fallbacks to preserve upgrade coordinate integrity
   - Consistent application across all update modes (auto, --next, --prev, update-all)


P: input names vs bead names create coupling and limit workflow flexibility during development
D: input map system to decouple input names from source bead names
   Architecture:
   - input_map: JSON file (meta/input.map) mapping input_name → bead_name
   - Default behavior: input_name maps to itself when no explicit mapping exists
   - Operational metadata: input maps are mutable and don't affect bead identity
   - Separate from immutable content: input maps excluded from manifest validation

   Persistence design:
   - Workspace: input_map property with JSON file persistence (meta/input.map)
   - ZipArchive: input_map property reading from archive, unpack_meta_to() restores to workspace
   - Storage: uses persistence.zip_dump() directly (not add_string_content()) to avoid manifest inclusion
   - Exception handling: FileNotFoundError for workspace, KeyError for ziparchive (zipfile API)

   Command behavior (when mappings change):
   - input add: Sets initial mapping to added bead name (calls set_source_name)
   - input map: Changes mapping to specified bead name
   - input update <explicit_bead>: Updates mapping to new bead name when explicit bead specified
   - input load: Preserves existing mappings (never modifies input_map)
   - input update (no explicit bead): Uses existing mapping for search, preserves mapping
   - input update --prev/--next: Uses and preserves existing mapping

   Key implementation insight:
   - Shared utility _check_load_with_feedback() must NOT set mappings (used by both add and load)
   - CmdAdd explicitly calls workspace.set_source_name() after loading
   - CmdLoad only loads, never modifies mappings
   - CmdUpdate sets mapping only when user provides explicit bead reference

   Benefits:
   - Decouples input names from source bead names for flexible development workflows
   - Enables input renaming without losing bead references
   - Supports mapping inputs to differently-named beads of same kind
   - Maintains backward compatibility (archives without input_map work seamlessly)
   - Preserves mappings across save/edit cycles for development continuity


P: input update safety - prevent accidental constraint violations during updates
D: three-level verification system with explicit bypass flags
   Problem context:
   - Search filters beads, but bugs could bypass constraints
   - Users need safety checks before actual data replacement
   - Different update modes need consistent safety guarantees
   - Clear user intent (file paths, explicit names) should skip verification

   Verification architecture:
   - Defense-in-depth: verification is redundant with search but catches bugs
   - Three independent constraints: name, kind, time (downgrade)
   - Each constraint can be relaxed independently or all bypassed with --force
   - Verification runs after search, before actual input update

   Name verification:
   - Only runs when no explicit bead name given (default update mode)
   - Skipped for file paths and explicit bead names (clear user intent)
   - Checks archive.name matches workspace.get_source_name(input.name)
   - Can be relaxed with --no-name or --force
   - Error message: "Name change detected: old → new. Use --no-name or --force to allow."

   Kind verification:
   - Always runs (no implicit bypass)
   - Checks archive.kind matches input.kind
   - Can be relaxed with --no-kind or --force
   - Error message: "Kind mismatch: expected KIND1, got KIND2. Use --no-kind or --force to allow."

   Time verification (downgrade detection):
   - Prevents updating to older versions by default
   - Checks archive.freeze_time >= input.freeze_time
   - Implicitly allowed by temporal navigation: --prev, --next, --time
   - Can be explicitly allowed with --allow-downgrade or --force
   - Error message: "Downgrade detected: TIME1 → TIME2. Use --allow-downgrade or --force to allow."

   Bypass flags:
   - --force: Bypass ALL verifications (name, kind, time)
   - --allow-downgrade: Bypass only time verification
   - --no-kind/--no-name: Relax search AND verification for that constraint

   Implementation location: bead_cli/input.py:357-402
   - _verify_archive_constraints(input, archive, args, workspace, explicit_bead_name)
   - Called after search succeeds, before _update_input()
   - Uses match_strategy enum to check --no-kind/--no-name state
   - explicit_bead_name parameter controls name verification skip

   Key design insight: File paths indicate clear user intent
   - File path given → user explicitly chose this specific archive
   - Explicit bead name given → user explicitly requested this bead
   - Default update (no args) → verify name matches to prevent surprises
   - This prevents verification from being overly restrictive

   Test isolation principle:
   - When testing one constraint failure, relax others to avoid false positives
   - Example: kind mismatch test uses newer timestamp (no downgrade)
   - Example: downgrade test uses same kind (no kind mismatch)
   - Ensures each test verifies exactly one constraint

   Benefits:
   - Catches search bugs before data replacement
   - Consistent safety across all update modes
   - Clear error messages suggest appropriate flags
   - File paths and explicit names bypass unnecessary checks
   - Each constraint independently relaxable for flexibility


P: naming for computation lifecycle stages
D: Computation base class with Workspace and Bead subclasses
   Core insight:
   - A bead represents a frozen computation: output = code(*inputs)
   - Workspace and frozen bead are the same computation in different lifecycle stages
   - Both share core identity: kind (what type), name (which one), inputs (dependencies)

   Recipe analogy:
   - Computation = Recipe identity: what dish (kind), dish name (name), ingredients list (inputs)
   - Workspace = Kitchen workspace: actively cooking with ingredients and recipe steps
   - Bead = Finished dish: frozen result with timestamp and provenance

   Class hierarchy:
   ```
   Computation:
     - kind, name, inputs: Core computation identity
     - get_input(name): Helper to look up input by name

   Workspace(Computation):
     - Mutable development environment
     - Attributes can change until frozen

   Bead(Computation):
     - Immutable frozen snapshot
     - Adds: content_id, freeze_time_iso, box_name for provenance
   ```

   "Is-a" test validation:
   - ✓ "Workspace is a Computation" - correct
   - ✓ "Bead is a Computation" - correct
   - Attributes flow: Workspace → freeze → Bead

   Benefits:
   - Natural lifecycle progression: develop → freeze → archive
   - Clear semantic distinction: mutable vs immutable
   - Recipe analogy provides intuitive mental model
